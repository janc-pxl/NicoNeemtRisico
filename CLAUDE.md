# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project
Interactive learning webapp that teaches students risk management (risicomanagement). Part of the PXL Hogeschool "Projectmanagement" course series, next to AgileForNigel, TeachBertPERT, TijdVoorKwaliteit and PMTheBasics.

## Source materials (in `source/` folder)
- `source/006 Risicomanagement.md` — the lesson content and structure (copied from `pxl-projectmanagement/docs/`)
- `source/009-risicomanagement.md` — the slides (generated from the PowerPoint, with speaker notes). Slide 4's notes hold the core case: a cyclist at a crossing, "Haal ik het?" (kans), "Wat kan er gebeuren?" (gevolg), "Wat als de auto een trein is?"
- `source/2025_10_huisstijlhandboek.pdf` — PXL corporate identity / huisstijlhandboek
- `source/1314_logo_pxl_bol_witrand.png` — original PXL logo (high-res)

## Requirements
- Single-page scroll layout (all sections on one page, nav links are anchor scrolls)
- Clean, modern design
- Max-width: 1100px (optimized for 1920x1080 student screens)
- Games in **vanilla JavaScript** on a `<canvas>`, no libraries, no image files (all pixel art is drawn in code)

## Hosting — GitHub Pages
The site is published via GitHub Actions to GitHub Pages.

- **Workflow**: `.github/workflows/deploy.yml` — triggers on every push to `main`
- **Source setting**: GitHub Pages → Source must be set to **GitHub Actions** (in repo Settings → Pages)
- No build step — the entire repo root is uploaded as the Pages artifact
- `index.html` only redirects to `risico.html`, so the root URL works too
- **Gotcha:** Pushing workflow files requires the `workflow` OAuth scope. If rejected, add the file via GitHub web UI instead.

Same design tokens, typography, nav (hamburger + scroll spy), footer, badges, callouts, progress bar and summary card as the sibling repos (see `../AgileForNigel/CLAUDE.md`).

**Extra tokens on this page:** `--c-kans` (blue, #3971c0: just dark enough for 4.5:1 on `--bg` as small text, e.g. the matrix axis label) = Kans, `--c-gevolg` (orange-brown) = Gevolg, `--c-risico` (black) = Risico; reused on cards, scales, sliders, matrix axes and formulas. **Numerals:** Raleway defaults to old-style figures (a "1" sits low, "1 tot 4" looks lowercase), so `body` sets `font-variant-numeric: lining-nums` for the whole page.

**Text sizes:** labels in the page fonts (Raleway/Arial) are at least ~12 px (.72-.75rem: matrix cell scores, Gantt weeks and markers, poker card words, team roles, mirror table heads); a whole-page critique found several at 9-11 px. Exceptions: the arcade font (its glyphs read larger), the post-its on the register matrix, and the 18 px cells of the compact "Jouw keuze" matrix on phones. Measure fit in the DOM when changing them (poker cards are 46 px wide on phones, hence the soft hyphen in `RR_K`'s "gemid­deld"). `p` uses `text-wrap: pretty`, `h2-h4` `text-wrap: balance`.

**Arcade look:** the game frame is black with a gold border; HUD, overlays and toasts use the Google Font **Press Start 2P** (`--arcade`). Page text stays Raleway/Arial.

## Architecture
Single-file HTML page (`risico.html`) with inline `<style>` and `<script>` — no build step, no framework.

**Game engine (shared):** a Frogger-style engine, `FrogGame(root, opts)`, used by every game on the page. Canvas 416x288 (13x9 tiles of 32px; pixel art in units of 2px, `FP`), scaled with `image-rendering: pixelated`.
- Sprites are drawn in code with `frogPainter` (`r` rect, `line` Bresenham, `mask` text pattern) into offscreen canvases. Nico (`NICO_TOP` + `NICO_LEGS_A/B`, seen from behind on a bike, gold helmet). Road users in `FROG_KINDS` (wandelaar, jogger, kar, fietser, brommer, auto, vrachtwagen, trein), each with random color variants and a flipped copy for leftward lanes.
- A level config has 9 `rows` (row 0 = `goal`, row 8 = `start`), surfaces (`grass`, `path`, `cobble`, `plein`, `road`, `bike`, `rail`, `ballast`, `berm`), plus optional `crossRoad`, `signals`, `barriers` (level crossing) and `tunnel` (L4). Background is pre-rendered by `frogDrawBg`.
- Lanes: `frogLaneInit/Update/Hit`. Spacing via `gap` (tiles) or `period` (seconds). Train lanes use a schedule (`train`, `every`, `warn`, `first`) with warning lights and barriers.
- Rules: 5 hearts, a hit costs `cfg.g` hearts (= gevolg), Frogger reset to start; `need` crossings to win. An attempt starts when Nico leaves the start row. Stats: attempts, hits, damage, time, tunnel. `opts.onEnd(result)` after win or game over.
- Controls: arrows/WASD (only while the game element has focus), swipe on the canvas, D-pad on `pointer: coarse`, M toggles music. The rAF loop only runs while the game is visible.

**Jan en Lowie (`DUO`):** the two lecturers (Jan Castermans and Lowie Vangaal) replace Nico on every end screen of both games. Arcade "boss" sprites of 24 × 32 units (drawn at 2 px per unit, like Nico), front view, casual outfits, drawn in code from their photos (the photos are not in the repo, on purpose: the site is public).
- Jan (left, x 44): short dark brown hair with a high hairline, dark full beard and moustache, broad smile with teeth, brown eyes, navy polo. Lowie (right, x 372): long straight ginger hair with a centre parting over the shoulders, ginger moustache, goatee and eyebrows, blue eyes, closed smile, black T-shirt with grey stripes. No glasses. Names "JAN" and "LOWIE" in the arcade font above their heads.
- "GEHAALD!": classic two-step bop (`DUO_DANCE`, 4 frames of 0.25 s: step left, knees, step right, knees; happy closed eyes, Lowie's hair sways) with confetti. "GAME OVER": shock (arms up, wide eyes), tipping backwards inward (`fallDir`), landing at `DUO_LAND`, one small bounce, then lying with X-eyes and circling stars; `thud` sound on landing and bounce. Names sink along with the fall.
- Rendered by `duoRender` on a `.frog-duo` canvas (416 × 288) that `showOverlay` puts behind the overlay text; animated from the game loop via `g.duo`. On phones (≤ 620 px) the end screen hides the text and stats (`.frog-overlay.end`) so the duo stays visible.

**Sound (`FrogAudio`):** everything is synthesized with the Web Audio API, no audio files. The AudioContext is created on the first user gesture (`start()` or a sound button), because of browser autoplay rules.
- Music: each of the four levels has its own original song in `FROG_SONGS` (`startMusic(owner, tempo, songId)`, the level passes `cfg.song` = its id). The user asked for songs that sound like well-known tracks; we only copy the **style** (mood, tempo, sound, structure), never melodies, riffs or chord progressions, because the site is public:
  - `park`, rustige new wave in de stijl van The Police, 116 bpm: steady guitar arpeggio with chorus and a dotted-eighth echo, quarter-note bass, rimshot, a soft melody in bars 5-8.
  - `markt`, vrolijke 80s synthpop in de stijl van a-ha, 150 bpm: bright detuned saw lead, octave bass, chord stabs on the offbeat, four-on-the-floor.
  - `overweg`, spionagethriller (the user first asked for MGMT, then found it not threatening enough and asked for "the Bond theme"; we made an original suspense track instead), D minor, 120 bpm: a staccato sawtooth ostinato that circles the root chromatically (`FS_OVER_OST`, deliberately not the notes of the Bond vamp), a dark open-fifth drone, a sparse twang motif on the echoing pluck, short brass stabs, a heartbeat kick and a ticking-clock hi-hat; the loop ends unresolved on A. **Tension layer:** voices with `tension: true` and the song's `tensionDrums` only play while `FrogAudio.tension` is on; the game sets it every frame while it owns the music and the level-crossing lights blink (`g.warning`), so a 16th-note tremolo and extra kicks and hats join when a train is coming.
  - `steenweg`, nu-metal in de stijl van System of a Down, 132 bpm, drop D: distorted power chords (root, fifth, octave through a WaveShaper) with palm-muted chugs and open "!" chords, sawtooth bass, double kick and crashes.
  Patterns are written in sixteenths (`"D4"`, `"."` = hold, `"-"` = rest, `"!"` = open chord) with helpers `fsE8`, `fsQ4`, `fsW1`; `frogPrepareSong` turns them into events per step and throws if a song does not have 16 steps per bar. Instruments live in `FrogAudio.inst` (pluck, lead, stab, pad, bass, dist) and `FrogAudio.drum` (kick, snare, rim, hat, open, crash); each song gets its own chain (`buildSongChain`, optional echo) that fades out on stop. **Every note's gain starts at 0.0001**, and the distortion curve has an odd number of points so silence maps to exactly 0: without both, notes scheduled ahead leaked a DC offset through the WaveShaper. Levels were balanced by rendering 8 s of each song in an `OfflineAudioContext` (rms ≈ 0.04-0.05).   - `rad` (the wheel, the user asked for "a typical TV game-show tune"; original, not the theme of an existing show), F major, 136 bpm: a cheesy progression (I, III7, IV, iv, I, VI7, II7, V7, `FS_RAD_CH`), a fat brassy saw lead, organ-like pad chords, a bouncy staccato bass with chromatic approach notes, Charleston-style brass stabs (3+3+2), a shuffle hi-hat, crashes and a snare fill in bar 8. Its `tensionDrums` are a snare roll (drum `roll`): the wheel's loop turns `FrogAudio.tension` on while `spinAnim` runs, so the roll plays during every spin and stops when the wheel lands. `radOwner.cfg.song = 'rad'`.
  The free-play sandbox keeps the original 8-bar chiptune loop (`FROG_TUNE`), scheduled in eighths.
  Everything is scheduled with a 25 ms lookahead timer. Only one game owns the music (`FrogAudio.owner`). It plays only while that game is active and visible, and stops on game over, win, level change or a hidden tab.
- Effects (`FrogAudio.play`): hop, start, cross, hit (heavier and lower for a higher gevolg), win, over, bell (every 0.42 s while the level-crossing lights blink), horn (when a scheduled train arrives), tunnel, thud, and for the wheel and the flip cards: tick, pick, meh, coin, shield, ouch.
- Two HUD buttons per game and on the wheel (`[data-snd="music"|"sfx"]`, `aria-pressed`) switch music and effects for the whole page; `FrogAudio.toggle` syncs every `[data-snd]` button. The choice is saved in `localStorage` (`nico-risico-audio-v1`, try/catch). Do not reproduce existing game music; keep the tune original.

**Progress (`Progress`):** everything the student does survives a reload (a whole-page critique found that one refresh wiped 45+ minutes of work). One localStorage key, `nico-risico-progress-v1` (try/catch), holds one plain-data snapshot per exercise: `frog` (`frogState`), `sb` (sliders, history and the last simulation's seed, so `simShow` redraws the same 100 dots), `coin`, `rad` (`RAD_KEEP` fields of `st`; never mid-spin, then the previous state stays), `ww` (an answered card already counts), `ld`, `rr`.
- Each module saves after every change and restores with `Progress.restore(part, fn)` **before** its first render. While restoring, `Progress.restoring` is on: nothing is saved and nothing takes focus. `finish(true)` (wheel) and `ldLaunch(true)` redraw a result quietly (no sound, announcement, scroll or focus). A restore that throws (old or broken data) drops only that part, which starts fresh, so validate the shape before assigning. Watch the order: the wheel and Lanceerdag only call `loadScenario(0)` / `ldReset()` when nothing was restored, because those save a fresh state.
- `Progress.done(anchor)` remembers finished parts by their h3 id (`frog-levels`, `frog-wat-als`, `pn-munt`, `pn-rad`, `pp-waar`, `pp-lancering`, `rr-poker`, `rr-lijn`, `rr-monitor`; grouped in `PROGRESS_SECTIONS`); it only ever turns on. `progressRender` shows them in the nav chip `#nav-chip` ("2/9", gold-filled "✓ 9/9" when all are done; right of the nav next to the hamburger and opening the same menu, so it stays visible on phones where the breadcrumb is cut; 36 px tall on touch screens; `navToggle`/`navClose` keep `aria-expanded` in sync on both buttons), in the line under each section h2 (`.sec-meta`: "2 delen · ongeveer 25 minuten" plus " · 1 van 2 afgewerkt" or " · ✓ afgewerkt"; the minutes are estimates: 25, 20, 15 and 25), as ✓ or "1/2" in the nav dropdown, as "Nog te doen: …" links per row in `#meenemen`, and in the notice `#resume` at the top of `<main>` ("Welkom terug", "Ga verder: <first unfinished part>").
- **Two tabs:** `write(part)` re-reads localStorage and writes back only its own part (plus the union of `done` and `touched`), never the tab's whole in-memory copy, and `set` skips a part whose content did not change (compared with `progressStable`, key order ignored), so opening a second tab writes nothing. A `storage` listener: when another tab saves a part with different content (or wipes everything), this tab stops saving (`off`) and `onStale` shows the bottom toast "Deze pagina is ook open in een ander tabblad … Herlaad" (or "Je voortgang is gewist in een ander tabblad"). The whole-page critique found that a stale second tab silently put back old data. The tab you worked in last is always the one that saves.
- **Toast `#pr-toast`** (fixed at the bottom, black with a gold border, `role="status"`, close button and Escape): also used for the return. The browser restores the scroll position on reload, so the notice `#resume` at the top is usually out of view; 500 ms after `load` the toast repeats "Welkom terug" with "Ga verder", and hides once `#resume` scrolls into view (IntersectionObserver), on close or on Ga verder.
- The notice only appears when the data is `touched`: the first page load already saves fresh states, so a save only counts once the student has clicked or pressed a key. "Begin opnieuw" (notice) and "Wis mijn voortgang" (end of `#meenemen`, meant for shared lab computers) ask for confirmation (focus on Nee, Escape cancels), then `Progress.clear()` (stops all saving) and reload at the top. The scroll spy also sets `aria-current="location"`.

     **Tuning targets (keep these when retuning):** the user found the earlier versions too easy at kans 5 twice, and later found kans 3 too easy ("ik slaag er telkens in met kans 3 over te geraken, dat zou af en toe moeten falen"); a version with 5 lanes and no safe strip (bot hit 6-16%) was then too hard, while kans 4 and 5 were fine. Current layouts: kans 1-5 = 2, 3, 5 (a block of 3, a strip, a block of 2), 6 (one strip in the middle) and 7 lanes; `SB_GW` is 1 from kans 3 so trains are not harder than walkers there. Measure with an attentive bot that has perfect information (looks 0.4 s ahead, may step sideways or back, decides every 0.15 s; 4 × 40 crossings per cell): about 0% at kans 1-2, a few percent at kans 3 (current 3-4%), 25-35% at kans 4 (current 21-35%) and 55-90% at kans 5 (current 73-91%) for every gevolg. Real players do worse than that bot. A bot with reaction lag that ignores its own lag is far too pessimistic (it fails kans 3 even on the old, too easy settings), so do not tune against that.
     "Laat Nico 100 keer onvoorzichtig oversteken" runs `frogSimulate` headless on its **own traffic** (`frogSimCfg`), not on the playable level: always two lanes (`SIM_LAYOUT`) with the gevolg's road user, only the density `SIM_OCC` depends on kans, and Nico does not look (just rides on, 0.3 s per hop). The playable level's hit rate is far from linear (on the old level settings a careless Nico was hit ≈ 5/16/39/70/100%), which made "probeer kans 5 × gevolg 1 en daarna kans 1 × gevolg 5" give 1,00 vs 0,24 hearts and contradict the formula (found in a critique). `SIM_OCC` is calibrated so the hit rate ≈ kans × 12%: measured 13/26/37/48/61% for kans 1-5, the same for every gevolg within ±4 points, so 5×1 ≈ 0,64 and 1×5 ≈ 0,59 hearts per crossing. Re-measure (6 × 100 runs per cell) when changing lanes, `SB_KINDS` speeds or `SB_DWELL`. It shows 100 dots, measured kans × gevolg = average hearts lost per crossing, one sentence that bridges the scale ("Kans 2 op de schaal van 1 tot 5 (klein) is een inschatting in woorden. De simulatie meet dezelfde kans als getal …"), plus a history table of the last runs.

The question is coloured by type (gold kans, red bedreiging, black for one party); hover is neutral. The back shows the verdict ("Juist!" or "Niet juist" + "Jij koos: …"), both sides with reasons (or bedreiging/kans "als …" plus a strategy line for "allebei" cards), each group is labelled by event + question. Rendering is per card (`coinCardHtml(i)`, `coinProgress`): `coinAnswer` only swaps that card's back face, disables its front buttons and adds `.flipped` to the existing element, so the 0.6 s CSS flip really runs (re-rendering the whole grid with `innerHTML` used to skip it). Under the section lead, `.pn-term` explains the two meanings of "kans": waarschijnlijkheid (blue `--c-kans`, as in the formula) vs opportuniteit (gold `--c-pos-ink`).   2. `#pn-rad`: "Het Rad van Risico", all inside `#rad-app`. The CSS is scoped under `#rad-app` (class names like `.panel`, `.legend`, `.measure`, `.hint` are only safe there), all IDs start with `rad-`, and the JS lives in an IIFE that exposes `window.Rad` (inline `onclick="Rad.clickMeasure(...)"` etc., plus `Rad.toggleMeasure` and `Rad.skipSpin` for tests).
     - Model: slice size = kans, number = gevolg; red slices are threats, gold slices opportunities, the neutral slice (shown twice) absorbs probability. Three scenarios in `SCENARIOS` (Black Friday budget 70, Tomorrowland 80, PlayStation 9¾ 90), 5 spins (`SPINS`). Measures have `cost` (once) or `premium` (per spin) and `fx`: `pTo`/`vTo` (set), `p`/`v` (factor), `shield` (eigen risico). `buildWheel` applies them in a FIXED order (set, then factors, then shield) so the click order never matters (a bug the user found once). Probabilities are capped at 0.6.
     - Strategies per type: threats `Vermijden`, `Verminderen`, `Verzekeren`, `Overdragen`; opportunities `Exploiteren`, `Verbeteren`, `Delen`; `Accepteren` is never a button, it is what happens to slices without a measure. **Exploiteren** = invest alone: chance to 30%, keep all profit. **Delen** = invest together with a partner *die het beter kan* (the lesson's definition): about half the cost, a higher chance than exploiteren (45% webshop partner, 55% radiozender, 50% chipfabrikant), profit halved; `excludes` makes them mutually exclusive on the same opportunity. A critique found exploiteren always won (+25..30 vs delen +2.5..4.3 with the old 35% delen) and the mirror table promised "(bijna) zeker"; now exploiteren is best in Black Friday (+30 vs +16,8) and PlayStation (+25 vs +17,5), delen in Tomorrowland (+22,9 vs +20, the crew costs 25), and the best plan there contains delen. Do not raise exploiteren to ~0.6: with values like +60 per spin it would dwarf every other measure.
