# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project
Interactive learning webapp that teaches students risk management (risicomanagement). Part of the PXL Hogeschool "Projectmanagement" course series, next to AgileForNigel, TeachBertPERT, TijdVoorKwaliteit and PMTheBasics.

## Source materials (in `source/` folder)
- `source/006 Risicomanagement.md` — the lesson content and structure (copied from `pxl-projectmanagement/docs/`)
- `source/009-risicomanagement.md` — the slides (generated from the PowerPoint, with speaker notes). Slide 4's notes hold the core case: a cyclist at a crossing, "Haal ik het?" (kans), "Wat kan er gebeuren?" (gevolg), "Wat als de auto een trein is?"
- `source/2025_10_huisstijlhandboek.pdf` — PXL corporate identity / huisstijlhandboek
- `source/1314_logo_pxl_bol_witrand.png` — original PXL logo (high-res)

## Requirements
- Single-page scroll layout (all sections on one page, nav links are anchor scrolls)
- Clean, modern design
- Max-width: 1100px (optimized for 1920x1080 student screens)
- Games in **vanilla JavaScript** on a `<canvas>`, no libraries, no image files (all pixel art is drawn in code)

## Hosting — GitHub Pages
The site is published via GitHub Actions to GitHub Pages.

- **Workflow**: `.github/workflows/deploy.yml` — triggers on every push to `main`
- **Source setting**: GitHub Pages → Source must be set to **GitHub Actions** (in repo Settings → Pages)
- No build step — the entire repo root is uploaded as the Pages artifact
- `index.html` only redirects to `risico.html`, so the root URL works too
- **Gotcha:** Pushing workflow files requires the `workflow` OAuth scope. If rejected, add the file via GitHub web UI instead.

## Architecture
Single-file HTML page (`risico.html`) with inline `<style>` and `<script>` — no build step, no framework.

**Game engine (shared):** a Frogger-style engine, `FrogGame(root, opts)`, used by every game on the page. Canvas 416x288 (13x9 tiles of 32px; pixel art in units of 2px, `FP`), scaled with `image-rendering: pixelated`.
- Sprites are drawn in code with `frogPainter` (`r` rect, `line` Bresenham, `mask` text pattern) into offscreen canvases. Nico (`NICO_TOP` + `NICO_LEGS_A/B`, seen from behind on a bike, gold helmet). Road users in `FROG_KINDS` (wandelaar, jogger, kar, fietser, brommer, auto, vrachtwagen, trein), each with random color variants and a flipped copy for leftward lanes.
- A level config has 9 `rows` (row 0 = `goal`, row 8 = `start`), surfaces (`grass`, `path`, `cobble`, `plein`, `road`, `bike`, `rail`, `ballast`, `berm`), plus optional `crossRoad`, `signals`, `barriers` (level crossing) and `tunnel` (L4). Background is pre-rendered by `frogDrawBg`.
- Lanes: `frogLaneInit/Update/Hit`. Spacing via `gap` (tiles) or `period` (seconds). Train lanes use a schedule (`train`, `every`, `warn`, `first`) with warning lights and barriers.
- Rules: 5 hearts, a hit costs `cfg.g` hearts (= gevolg), Frogger reset to start; `need` crossings to win. An attempt starts when Nico leaves the start row. Stats: attempts, hits, damage, time, tunnel. `opts.onEnd(result)` after win or game over.
- Controls: arrows/WASD (only while the game element has focus), swipe on the canvas, D-pad on `pointer: coarse`, M toggles music. The rAF loop only runs while the game is visible.

**Jan en Lowie (`DUO`):** the two lecturers (Jan Castermans and Lowie Vangaal) replace Nico on every end screen of both games. Arcade "boss" sprites of 24 × 32 units (drawn at 2 px per unit, like Nico), front view, casual outfits, drawn in code from their photos (the photos are not in the repo, on purpose: the site is public).
- Jan (left, x 44): short dark brown hair with a high hairline, dark full beard and moustache, broad smile with teeth, brown eyes, navy polo. Lowie (right, x 372): long straight ginger hair with a centre parting over the shoulders, ginger moustache, goatee and eyebrows, blue eyes, closed smile, black T-shirt with grey stripes. No glasses. Names "JAN" and "LOWIE" in the arcade font above their heads.
- "GEHAALD!": classic two-step bop (`DUO_DANCE`, 4 frames of 0.25 s: step left, knees, step right, knees; happy closed eyes, Lowie's hair sways) with confetti. "GAME OVER": shock (arms up, wide eyes), tipping backwards inward (`fallDir`), landing at `DUO_LAND`, one small bounce, then lying with X-eyes and circling stars; `thud` sound on landing and bounce. Names sink along with the fall.
- Rendered by `duoRender` on a `.frog-duo` canvas (416 × 288) that `showOverlay` puts behind the overlay text; animated from the game loop via `g.duo`. On phones (≤ 620 px) the end screen hides the text and stats (`.frog-overlay.end`) so the duo stays visible.

**Sound (`FrogAudio`):** everything is synthesized with the Web Audio API, no audio files. The AudioContext is created on the first user gesture (`start()` or a sound button), because of browser autoplay rules.
- Music: each of the four levels has its own original song in `FROG_SONGS` (`startMusic(owner, tempo, songId)`, the level passes `cfg.song` = its id). The user asked for songs that sound like well-known tracks; we only copy the **style** (mood, tempo, sound, structure), never melodies, riffs or chord progressions, because the site is public:
  - `park`, rustige new wave in de stijl van The Police, 116 bpm: steady guitar arpeggio with chorus and a dotted-eighth echo, quarter-note bass, rimshot, a soft melody in bars 5-8.
  - `markt`, vrolijke 80s synthpop in de stijl van a-ha, 150 bpm: bright detuned saw lead, octave bass, chord stabs on the offbeat, four-on-the-floor.
  - `overweg`, spionagethriller (the user first asked for MGMT, then found it not threatening enough and asked for "the Bond theme"; we made an original suspense track instead), D minor, 120 bpm: a staccato sawtooth ostinato that circles the root chromatically (`FS_OVER_OST`, deliberately not the notes of the Bond vamp), a dark open-fifth drone, a sparse twang motif on the echoing pluck, short brass stabs, a heartbeat kick and a ticking-clock hi-hat; the loop ends unresolved on A. **Tension layer:** voices with `tension: true` and the song's `tensionDrums` only play while `FrogAudio.tension` is on; the game sets it every frame while it owns the music and the level-crossing lights blink (`g.warning`), so a 16th-note tremolo and extra kicks and hats join when a train is coming.
  - `steenweg`, nu-metal in de stijl van System of a Down, 132 bpm, drop D: distorted power chords (root, fifth, octave through a WaveShaper) with palm-muted chugs and open "!" chords, sawtooth bass, double kick and crashes.
  Patterns are written in sixteenths (`"D4"`, `"."` = hold, `"-"` = rest, `"!"` = open chord) with helpers `fsE8`, `fsQ4`, `fsW1`; `frogPrepareSong` turns them into events per step and throws if a song does not have 16 steps per bar. Instruments live in `FrogAudio.inst` (pluck, lead, stab, pad, bass, dist) and `FrogAudio.drum` (kick, snare, rim, hat, open, crash); each song gets its own chain (`buildSongChain`, optional echo) that fades out on stop. **Every note's gain starts at 0.0001**, and the distortion curve has an odd number of points so silence maps to exactly 0: without both, notes scheduled ahead leaked a DC offset through the WaveShaper. Levels were balanced by rendering 8 s of each song in an `OfflineAudioContext` (rms ≈ 0.04-0.05).   - `rad` (the wheel, the user asked for "a typical TV game-show tune"; original, not the theme of an existing show), F major, 136 bpm: a cheesy progression (I, III7, IV, iv, I, VI7, II7, V7, `FS_RAD_CH`), a fat brassy saw lead, organ-like pad chords, a bouncy staccato bass with chromatic approach notes, Charleston-style brass stabs (3+3+2), a shuffle hi-hat, crashes and a snare fill in bar 8. Its `tensionDrums` are a snare roll (drum `roll`): the wheel's loop turns `FrogAudio.tension` on while `spinAnim` runs, so the roll plays during every spin and stops when the wheel lands. `radOwner.cfg.song = 'rad'`.
  The free-play sandbox keeps the original 8-bar chiptune loop (`FROG_TUNE`), scheduled in eighths.
  Everything is scheduled with a 25 ms lookahead timer. Only one game owns the music (`FrogAudio.owner`). It plays only while that game is active and visible, and stops on game over, win, level change or a hidden tab.
- Effects (`FrogAudio.play`): hop, start, cross, hit (heavier and lower for a higher gevolg), win, over, bell (every 0.42 s while the level-crossing lights blink), horn (when a scheduled train arrives), tunnel, thud, and for the wheel and the flip cards: tick, pick, meh, coin, shield, ouch.
- Two HUD buttons per game and on the wheel (`[data-snd="music"|"sfx"]`, `aria-pressed`) switch music and effects for the whole page; `FrogAudio.toggle` syncs every `[data-snd]` button. The choice is saved in `localStorage` (`nico-risico-audio-v1`, try/catch). Do not reproduce existing game music; keep the tune original.

**Current sections in `risico.html`:**
- `#kans-gevolg` — Risico = Kans × Gevolg. Intro with Nico's portrait (drawn from the sprite), three formula cards (Kans "Haal ik het?", Gevolg "Wat kan er gebeuren?", Risico) and the zone legend, then:
  1. `#frog-levels` (prefix `frog-`): four levels in `FROG_LEVELS`, one per quadrant: Het park (K1 G1), Marktdag (K5 G1), De overweg (K1 G5, trains with lights and barriers), De steenweg (K5 G5, with a fietstunnel = vermijden). Tabs, the game `#frog-main`, and an analysis panel `#frog-analysis` that appears after a level ends: stats, then the student rates kans and gevolg (1-5, `RISK_K`/`RISK_G`). Within ±1 of the level's values = good; otherwise level hints (`hintK`/`hintG`), revealed after the second try. Reveal shows the formula, zone, explanation and an IT-project example (`it`). Markers are added to the risk matrix (`riskMatrixHtml`). Summary when all four are analysed (same score 5 for markt and overweg, measures: preventie/repressie/vermijden/aanvaarden).
  2. `#frog-wat-als` (prefix `sb-`, `sim-`): "Wat als de auto een trein is?" Sliders for kans and gevolg drive a playable sandbox (`frogSandboxCfg`): gevolg picks the road user (wandelaar, fietser, brommer, auto, trein), kans sets how busy it is: number of lanes (`SB_LAYOUT`, 2 to 7 lanes; kans 5 = 7 lanes with no safe strip), speed (`SB_SPEED`, 0.8x to 1.5x, varied per lane with `SB_VARY` so gaps never line up) and density (`SB_OCC`, gaps between 0.6x and 1.25x of the mean so there are no long holes). Slow road users are easier to dodge, so at high kans their stream is denser (`SB_GF`, weighted per kans by `SB_GW`); that keeps the difficulty about the same for every gevolg. Nico's hitbox is `FROG_HIT_L/R` (5..27 px of the tile, shared with the levels).
     **Tuning targets (keep these when retuning):** the user found the earlier versions too easy at kans 5 twice. Measure with an attentive bot that has perfect information (looks 0.4 s ahead, may step sideways or back, decides every 0.15 s): it must still be hit in roughly 50-75% of crossings at kans 5 for every gevolg (current: 54-76%), and close to 0% at kans 1-3. Real players do worse than that bot.
     "Laat Nico 100 keer onvoorzichtig oversteken" runs `frogSimulate` headless: a careless Nico glances 0.1 s ahead at the next lane (`SIM_LOOK`), goes anyway after 1 s of waiting (`SIM_PATIENCE`), no sidesteps. Measured hit rates ≈ 2/15/35/73/98% for kans 1-5, about the same for every gevolg. It shows 100 dots, measured kans × gevolg = average hearts lost per crossing, plus a history table of the last runs.

- `#positief-negatief` — Positieve en negatieve risico's (badge "Risicostrategieën"). Lead with the lesson definition (bedreigingen vermijden/verkleinen/beheersen, kansen omarmen/versterken), then two parts. Colors: `--c-pos` (gold, kans) and `--c-neg` (red, bedreiging), each with `-bg` and `-ink`.
  1. `#pn-munt` (prefix `coin-`): warm-up "Twee kanten van dezelfde munt". Six flip cards (`COIN_CARDS`: lockdown, stortbui op Tomorrowland, AI-tool die code schrijft, strengere privacywet, hittegolf, licentieprijs 3D-software verdubbelt, the last one from Lowie's Matterport note on the slides). Front: the event and "Voor wie is dit een kans?" with two parties (correct side alternates by card index); the card flips (CSS 3D, both faces in one grid cell) and shows "KANS VOOR" (gold) and "BEDREIGING VOOR" (red) with a reason. Progress bar plus summary: kans or bedreiging depends on whose goals you look at, which bridges to the wheel.
  2. `#pn-rad`: "Het Rad van Risico", all inside `#rad-app`. The CSS is scoped under `#rad-app` (class names like `.panel`, `.legend`, `.measure`, `.hint` are only safe there), all IDs start with `rad-`, and the JS lives in an IIFE that exposes `window.Rad` (inline `onclick="Rad.clickMeasure(...)"` etc., plus `Rad.toggleMeasure` and `Rad.skipSpin` for tests).
     - Model: slice size = kans, number = gevolg; red slices are threats, gold slices opportunities, the neutral slice (shown twice) absorbs probability. Three scenarios in `SCENARIOS` (Black Friday budget 70, Tomorrowland 80, PlayStation 9¾ 90), 5 spins (`SPINS`). Measures have `cost` (once) or `premium` (per spin) and `fx`: `pTo`/`vTo` (set), `p`/`v` (factor), `shield` (eigen risico). `buildWheel` applies them in a FIXED order (set, then factors, then shield) so the click order never matters (a bug the user found once). Probabilities are capped at 0.6.
     - Strategies per type: threats `Vermijden`, `Verminderen`, `Verzekeren`, `Overdragen`; opportunities `Exploiteren`, `Verbeteren`, `Delen`; `Accepteren` is never a button, it is what happens to slices without a measure. **Delen = samen investeren**: about half the cost of exploiteren, chance 35%, profit halved; `excludes` makes exploiteren and delen on the same opportunity mutually exclusive. Each scenario has one absurd insurance (meteoriet, aliens, bliksem) whose risk is not on the wheel, and some measures that cost more than they yield.
     - Learning flow: clicking a measure first asks "Welke strategie is dit?" with only the options of that risk type (`STRAT_NEG`/`STRAT_POS`). Wrong: crossed out plus a mechanism hint (`STRAT_HINT`); after two wrong answers the answer is shown. `Verminderen` and `Verbeteren` get a second question, oorzaak (kans) or effect (gevolg), derived from `fx` (`ceOf`). Only then is the measure applied and the wheel animates. Re-selecting a measure in the same scenario skips the question. The mirror table (`.mirror`) above the measures shows the pairs Vermijden ↔ Exploiteren, Verminderen ↔ Verbeteren, Verzekeren/Overdragen ↔ Delen, Accepteren ↔ Accepteren.
     - Live meter: expected profit per spin (Σ kans × gevolg − premiums), without measures, expected end budget. The legend table shows kans, gevolg, kans × gevolg and the strategy per event.
     - Result: breakdown of the end budget (start, measures, premiums, wheel outcome per spin), a ghost run without measures with the same random numbers, expected end budget with and without measures, the best achievable expected end budget (`bestPlan`, brute force within budget and `excludes`), the strategy score (named right the first time), and net expected value per measure. The verdict judges choices (expected value) separately from luck: "Goede keuzes!", "Goed, maar het kan beter: ...", "Pech gehad, maar goede keuzes!", "Geluk gehad, maar te duur betaald.", "Je maatregelen kosten meer dan ze opbrengen.", "Je nam geen enkele maatregel."
     - Jan and Lowie stand beside the wheel (`hosts`, sprites from `DUO`) with speech bubbles; they react to measures, answers and spins (dance on gold, shock on red), and dance or fall at the end.
     - Sound via `FrogAudio` (effects `tick`, `pick`, `meh`, `coin`, `shield`, `ouch`, plus `win`/`over`; music: the `rad` game-show song with a snare roll while spinning). The wheel registers `radOwner` in `FROG_GAMES`, so music plays only while spinning and the wheel is visible. Music/effects buttons are synced across the whole page. The wheel's rAF loop only runs while `#rad-app` is visible.

- `#product-project` — Product- en projectrisico's (badge "Soorten risico's"). **No arcade here** (the user asked for a calmer, non-arcade style after two arcade sections): page fonts, no sound, no Jan and Lowie. CSS scoped under `#product-project`, keyframes prefixed `pp` (`ppGlitch`, `ppBelt`, ...), JS in an IIFE that exposes `window.PP` for tests. Colors: `--c-product` (violet) and `--c-project` (teal), each with `-bg` and `-ink`. Running example: the app of the fictional festival **Vonk** (made up on purpose, not a real festival).
  - Intro: two concept cards (Productrisico "Werkt het product zoals de gebruiker verwacht?", Projectrisico "Halen we de oplevering?") and the rule of thumb "kijk waar het gevolg landt": at the user = product risk, in time/budget/scope = project risk.
  - Shared parts: `PPPhone` draws a phone with the Vonk app (feature tiles from `PP_FEATURES`: line-up, timetable, kaart, cashless, meldingen, chat), star rating and a quality bar; below a quality threshold small beetles (`PP_BUG_SVG`) crawl over the screen (random walk in a rAF loop, count = (92 − quality) / 7). `glitch()` shakes the screen; `setFeature` removes or adds a tile.
  1. `#pp-waar` (prefix `ww-`): "Waar landt het gevolg?" 12 risk cards (`WW_CARDS`) slide in one by one (the word "band" is avoided in the text: on a festival page it reads as a music band). The student sends each card to the app (product: quality −8, glitch, a beetle) or to the project board (meters tijd/budget/scope). Wrong answers shake the card first; every card shows a short explanation and a "Volgend risico" button. The last card ("test het team een week minder") is `both`: it lands on the board and a spark flies to the app. Progress bar plus summary.
  2. `#pp-lancering` (prefix `ld-`): "Lanceerdag", six problems (`LD_EVENTS`, labelled "Probleem 1 tot 6", spread over the planning with `ldT`), three options each with visible costs (`+x week`, `xk euro`, `kwaliteit −x`, `− kaart`, `+ chat`). Resources: buffer 2 weeks (planned launch week 4, festival week 6), reserve 50k, quality starts at 80 with a minimum of 60. A Gantt chart (bars shift on delay, buffer zone, "Poorten open", "vandaag") and a budget gauge with a needle. Problem 5 is a product risk, the rest project risks. Lanceerdag shows stamps (op tijd, binnen budget, app werkt), visitor reviews that match the choices, a 2×2 matrix (Geslaagde lancering, De Sonos-val, Goed product mislukt project, Allebei mis) and every choice tagged (opgevangen met tijd/budget/scope, scope bewaakt, doorgeschoven naar het product).
     **Design rules the user insisted on:** every option must cost something you can see, so no option is simply best (only refusing the chat feature stays free on purpose: guarding scope is a good choice). Costs must match the text ("een week te laat" = +1 week). Removing the map costs quality −5 (users miss a feature). The faster App Store review is a real risk: it costs 3k euro of work and has a 50% chance of +0 weeks and 50% of +1.5 weeks (rolled with `Math.random`). With these numbers, of the sensible paths (no "negeren", no "twee weken wachten") about 23% end in a successful launch, 32% in the Sonos trap, 37% late and 8% both wrong. Re-check this when changing numbers.

- `#register` — Risicomatrix en risicoregister (badge "Risicobeheer"). Calm style like the product/project section (no arcade, no sound, no Jan and Lowie). CSS scoped under `#register`, keyframes `rrDrop` and `rrPulse`, JS in an IIFE that exposes `window.RR` for tests. Case: festival project Vonk 2026 with three fictional colleagues (`RR_TEAM`): Sara (veiligheid), Mehdi (techniek), Ellen (programmatie, personeel en financiën). Their quotes must show their point of view (safety, technology, money), never indifference.
  - Intro: three step cards (Inschatten, Beoordelen en beheersen, Monitoren) following the six steps on the slides.
  - Layout: content left, a **sticky risk matrix** right (`.rr-aside`, top 70px) that follows all three parts; on screens ≤ 900px it moves to the top and sticks under the nav (top 54px). Each risk is a yellow post-it (`.rr-note`) positioned by percentage in a 5×5 grid and animated with CSS transitions; notes in the same cell stack.
  1. `#rr-poker` "Risico-poker": six risks (`RR_RISKS`) that together cover **every zone** (the user asked for at least one per zone): toiletten 4×1 laag, headliner 2×4 and vrijwilligers 4×2 middel, cashless 3×4 and vergunning 2×5 hoog, storm 4×5 kritiek. The student picks a card for kans and impact, then all cards flip (CSS 3D) with a quote per colleague; spread, consensus with reason and a comparison with the student's pick; "Plak op de matrix" drops the post-it.
  2. `#rr-lijn` "Trek de lijn en vul het register": a slider ("Vonk aanvaardt risico's met een score tot X", 1 to 20) draws a staircase line (SVG) and hatches the cells above it. Locking asks for confirmation if the storm is accepted or everything is above. Every risk above the line becomes a register row with owner (buttons show name and role; any choice is accepted with a tip about the most logical owner), datum van relevantie, preventieve actie and noodplan (three options each, with decoys of the other type; two wrong tries reveal the answer). **The register order is frozen when the line is locked** (`rr.order`), so rows do not jump when a measure lowers the score; new rows go at the bottom.
     Effects on the matrix: a preventive action lowers kans or impact (`fx`); **a noodplan always lowers the impact by 1 and never the kans** ("De kans blijft gelijk, de impact daalt"), including the noodplans added during monitoring.
  3. `#rr-monitor` "Het register leeft": a timeline with six moments (`RR_MON`): the permit (closed, or just in time by luck if it was accepted), the headliner confirms (date of relevance, kans down), a new risk hittegolf (student picks the preventive action; the EHBO post is the noodplan), only 70% of the volunteers confirmed (kans up; if it crosses the line it is added late with only a noodplan), storm on Saturday 21:00 and cashless outage on Sunday 14:00. Those two incidents are handled by the chosen owner with the noodplan, or end in chaos if the risk was accepted. Evaluation shows "voorbereid op X van de 2 incidenten", the status of every risk and "Opnieuw, met een andere lijn" (keeps the estimates, resets line and register).

## Development
No build commands. Open `risico.html` directly in a browser, or start the `risico` preview from `.claude/launch.json` (`python -m http.server 8765`). The deploy workflow uploads the entire repo root as a static site.
